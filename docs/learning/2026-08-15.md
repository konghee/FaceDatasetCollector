## 1. Coordinator가 뭔지 모르고 복붙했다

다른 프로젝트에서 코드를 가져와 붙였더니 동작은 했는데, `Coordinator`가 왜 있어야 하는지 몰랐습니다.

**SwiftUI의 `View`는 struct입니다.** 값 타입이라 화면이 다시 그려질 때마다 새로 만들어지고 버려집니다. 반면 `ARSCNView`는 class고 화면에 붙어 계속 살아 있습니다.

문제는 `ARSCNViewDelegate` 같은 프로토콜이 **`@objc` 프로토콜**이라는 것. `@objc`는 Objective-C 런타임 방식으로 호출된다는 표시이고, 그 런타임은 **class에만 있는 메타데이터**(셀렉터 테이블 등)로 메서드를 찾아 호출합니다. struct는 그런 정보가 아예 없어서 **컴파일 자체가 안 됩니다.** `NSObject`를 상속해야 하는 것도 같은 이유 — `NSObject`가 그 메타데이터를 제공하는 기반 클래스입니다.

그래서 SwiftUI가 내놓은 해법이 Coordinator 패턴입니다. `makeCoordinator()`로 한 번만 만들어지고 SwiftUI가 계속 살려 두는, **struct와 UIKit 사이의 안정적인 다리** 역할의 class.

> 확인법: 프로토콜인지 아닌지는 Xcode에서 **Cmd+클릭**(Jump to Definition)하면 `protocol` 키워드가 보입니다. Option+클릭(Quick Help)은 요약만 보여줘서 부족합니다. Quick Help 아래 "Open in Developer Documentation"으로 가면 각 메서드가 언제 불리는지 나옵니다.

## 2. `makeCoordinator()`의 반환 타입을 `-> ()`로 썼다

```swift
func makeCoordinator() -> () {   // ❌ Void를 반환한다는 뜻
    Coordinator()
}
```

`()`는 `Void`입니다. 본문은 `Coordinator()`를 반환하는데 타입이 안 맞아 컴파일이 깨졌습니다.

핵심은 **`context.coordinator`의 타입이 바로 이 반환 타입으로 결정된다**는 것. `-> ()`면 `context.coordinator`도 `Void`가 되고, `view.delegate = context.coordinator`에서 타입 에러가 납니다. 에러 메시지는 델리게이트 대입 줄에 뜨지만 원인은 위에 있었습니다.

호출 순서도 여기서 이해됐습니다. `makeCoordinator()`가 `makeUIView()`**보다 먼저** 불리는 건, 후자 안에서 전자의 결과를 쓰기 때문입니다.

## 3. 세션 하나에 델리게이트가 둘이었다

가장 오래 헷갈린 부분. 이 앱은 같은 `ARSession`에 델리게이트를 **두 개** 꽂아 씁니다.

| 자리 | 객체 | 하는 일 | 등록 위치 |
|---|---|---|---|
| `ARSession.delegate` | `ARSessionProxy` | 얼굴 값 → 화면의 각도 표시 | `manager.start()` 안 |
| `ARSCNView.delegate` | `Coordinator` | 얼굴 위에 그릴 3D 노드 | `makeUIView()` 안 |

둘은 서로를 전혀 모릅니다. 하나는 "지금 고개가 몇 도 돌아갔나"를 SwiftUI에 전달하고, 다른 하나는 "이 얼굴 위에 뭘 그릴까"를 SceneKit에 전달합니다. 하는 일이 달라서 분리돼 있는 것.

## 4. `didUpdate`에 반환값이 없는데 어떻게 화면이 바뀌나

```swift
func renderer(_ renderer: SCNSceneRenderer, didUpdate node: SCNNode, for anchor: ARAnchor) {
    ...
    faceGeometry.update(from: faceAnchor.geometry)   // 반환값 없음
}
```

"업데이트를 어떻게 캐치해서 다시 그리지?"라고 생각했는데, 전제가 틀렸습니다.

`nodeFor`에서 반환한 노드는 **이미 3D 씬 안에 들어가 있습니다.** `SCNNode`와 `SCNGeometry`는 class(참조 타입)라, `update(from:)`은 새로 그리는 게 아니라 **씬에 있는 그 객체의 정점을 제자리에서 바꿔치기**합니다. SceneKit은 매 프레임 씬을 그대로 다시 렌더링하므로 바뀐 내용이 자동으로 반영됩니다. 그래서 반환값이 필요 없습니다.

**어느 함수를 부를지는 ARKit이 앵커의 UUID로 정합니다.** 처음 보는 UUID면 `nodeFor`(생성), 이미 아는 UUID면 `didUpdate`(갱신), 사라지면 `didRemove`. 내가 고르는 게 아니라, 각 경우에 *무엇을 할지*만 써 두면 시스템이 타이밍을 잡아 불러 줍니다.

## 5. git — 이슈에서 머지까지 한 사이클

```bash
gh issue create --title "..." --label enhancement     # → #1
git switch -c feat/1-add-face-mesh-to-camera          # 이슈 번호를 브랜치명에
git add <파일>                                         # git add . 는 쓰레기까지 담는다
git commit -m "카메라 뷰에서 얼굴 메시 추가"
git push -u origin feat/1-add-face-mesh-to-camera
gh pr create --body "Closes #1"                       # 머지 시 이슈 자동 닫힘
gh pr merge --squash --delete-branch
```

배운 것들:

- **`git switch -c`가 `git checkout -b`보다 낫다.** `checkout`은 브랜치 전환·파일 복구·커밋 체크아웃을 다 하는 다목적 명령이라 실수하기 쉽습니다(`git checkout .`은 파일을 되돌려버림). `switch`는 브랜치 전용으로 나온 명령이라 안전합니다.
- **`Closes #1`이 PR 본문에 있으면 머지될 때 이슈가 자동으로 닫힙니다.** 브랜치명에 번호가 없어도 동작합니다.
- **`gh pr merge`를 인자 없이 쓰면 대화형 프롬프트가 뜹니다.** `--squash --delete-branch`처럼 명시하는 편이 낫습니다.
- **이슈 → 브랜치 순서는 강제가 아닙니다.** 브랜치를 먼저 팠어도 PR에서 `Closes #N`으로 연결하면 됩니다. 브랜치명은 push 전이라면 `git branch -m 새이름`으로 자유롭게 바꿀 수 있습니다.

### squash merge가 그래프에 남기는 모양

머지 후 그래프를 보니 `feat/...` 브랜치가 `main` **아래에 떨어진 곁가지**로 남아 있어서 "머지가 안 된 건가?" 싶었습니다.

정상입니다. `--squash`는 브랜치를 main에 이어붙이는 게 아니라 **변경 내용만 모아 main에 새 커밋을 하나 만듭니다.** 내용은 같지만 다른 커밋(`1542c7a` vs `18e1160`)이라, 원래 브랜치는 main의 조상이 아니게 되어 갈라진 채 남습니다. 코드는 이미 main에 다 들어가 있습니다.

## 6. `.gitignore`는 이미 추적 중인 파일을 막지 못한다

`UserInterfaceState.xcuserstate`(Xcode 창 배치 상태)가 매 커밋마다 따라붙었습니다. `.gitignore`에 추가했는데도 계속 나왔습니다.

**무시 규칙은 아직 추적되지 않는 파일에만 적용됩니다.** 이미 git이 추적 중인 파일은 추적 목록에서 빼줘야 합니다.

```bash
git rm --cached <파일>    # --cached: 인덱스에서만 제거, 로컬 파일은 그대로
```

## 7. 빌드 설정도 코드다

iPad 지원을 켜면서 "Xcode에서 체크박스만 눌렀는데 커밋할 게 있나?" 싶었는데, 있었습니다.

Xcode의 General 탭에서 바꾼 설정은 전부 **`project.pbxproj`에 텍스트로 저장**됩니다. 이게 커밋되어야 다른 사람이 클론했을 때 같은 설정으로 빌드됩니다. **`git status`에 뜨면 그건 버전 관리 대상**이라고 보면 됩니다.

또 하나 — Xcode는 **값을 실제로 바꿨을 때만** 키를 씁니다. 기본값을 눈으로 보고 "이미 되어 있네" 하고 넘어가면 파일에는 아무것도 안 남습니다. 체크박스를 직접 해제해야 키가 생깁니다.

## 8. iPad 세로 고정은 UI 취향이 아니라 데이터 문제였다

iPad 지원에서 진짜 위험한 건 화면 크기가 아니라 **회전**이었습니다.

`CaptureOrientation.derived`는 저장 이미지의 EXIF 방향을 `displayTransform(for: .portrait)`에서 역산합니다. 즉 **세로 고정을 전제로** 동작합니다. iPad는 기본값이 4방향 회전 허용이라, 지원 기기만 넓히고 방향을 잠그지 않으면 가로로 들고 찍은 사진이 **크래시도 경고도 없이** 누운 채로 데이터셋에 쌓입니다. 학습 단계에 가서야 발견되는 종류의 버그입니다.

`UIRequiresFullScreen = YES`도 같이 켰습니다. Split View에서는 방향 잠금이 무시되고, ARKit 세션도 정상 동작하지 않기 때문입니다.

ARKit 얼굴 추적은 **TrueDepth(Face ID)가 있는 iPad Pro에서만** 됩니다. Air / mini / 일반 iPad는 설치는 되지만 안내 화면만 뜹니다 — 버그가 아니라 `isSupported` 분기의 정상 동작입니다.
